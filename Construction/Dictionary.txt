=== CORE CONCEPT ===

The system is a directed multi-perspective theater.
One shared moment, multiple simultaneous views.

Audience View OFF = Rehearsal
Audience View ON = Live

---

=== OWNERSHIP / DEPLOYMENT ===

Producer
- Owner of the system instance (Location)
- Controls billing, library, policies
- May act as Director or Audience

Location
- A deployed instance of the software
- Owned by a Producer
- Contains Lots, Productions, Libraries, Users

Lot
- Collection of Venues within a Location
- Organizational grouping of performance spaces

Company
- Collection of participants (Cast + Crew)
- Associated with a Producer/Location

=== TOOLING ===

Tooling
- Reusable controls and inspection mechanisms that invoke or observe system actions
- Tooling may be used for development, operations, production, or audience interaction
- Tooling is not limited to debug use

Dev Tooling
- Controls used during construction and testing
- Examples:
  - trigger action manually
  - inspect snapshot
  - replay action history
  - simulate role behavior
  - stress test reactions

Operator Tooling
- Controls used to run, inspect, diagnose, and recover the system
- Examples:
  - inspect active sessions
  - inspect memberships
  - inspect storage state
  - verify invite flow
  - reset or revoke access
  - view service health

Production Tooling
- Controls used by producer, director, cast, or crew during setup, rehearsal, or live use
- Examples:
  - reveal
  - hide
  - speak
  - cue
  - assign
  - load asset
  - toggle production policy

Audience Tooling
- Narrow, safe controls available to audience participants
- Examples:
  - react
  - send note card
  - vote when invited
  - choose prompted options

Trigger
- A UI control, command, hotkey, macro, or programmatic mechanism that invokes an action
- Different triggers may invoke the same underlying action

Control Overlay
- A role-specific interface layer placed over or alongside a rendered view
- Used to expose controls or feedback without changing the underlying stage content

Stage Overlay
- A visual layer presented as part of the staged experience
- Examples:
  - banner
  - subtitle
  - cue marker
  - reaction indicator

Inspection
- Reading derived or stored system truth without mutating it
- Examples:
  - current visibility state
  - current participants
  - action history
  - policy state

Diagnostic
- A tooling function intended to identify failure, drift, or mismatch
- Examples:
  - connection test
  - permission check
  - stale session check
  - asset presence verification

Stress Test
- A high-load or repeated-action test used to measure behavior under pressure
- A stress test may be composed of the same smaller actions used in ordinary UI controls

Action UI Layer
- The first user-facing layer that exposes existing system actions through actual interface controls
- Distinct from backend action contract
- Should reuse the same underlying action model

Policy
- A configurable rule that governs what roles may do in a location, production, venue, or session
- Producer sets ceilings
- Director may set production defaults within those ceilings

Policy Toggle
- A discrete on/off policy switch
- Example:
  - actors_can_reveal

Permission Lattice
- The structured system that determines who may invoke which actions, against what targets, in which contexts
- More precise than simple role hierarchy

Role Gating
- Showing or hiding controls in the interface based on role
- UI convenience only unless backed by server enforcement

Authority Enforcement
- Server-side validation that determines whether an action is actually allowed
- The client may suggest an action; the server decides whether it is valid

Projection
- The role- and context-specific view produced from shared truth
- Projection is rendered, not stored as the only source of truth

Illusion Layer
- The part of the system that causes different viewers to perceive different realities from the same shared session
- Built from projection + rendering + action timing

Hub
- A venue or location on the map with higher navigational or symbolic importance
- Example:
  - Victory Theater as a map hub

Map Interface System
- The frontend navigation layer that renders visible venues spatially based on backend visibility rules

Spatial Venue Rendering
- Rendering venues as positioned nodes/icons on the map, where placement carries meaning

Venue Metadata
- Render-related information about a venue
- Examples:
  - slug
  - icon
  - position
  - priority
  - public/private state

Grant
- An explicit server-recognized permission or membership assignment that allows access to a venue, production, or function

Admission
- The act of allowing a participant into a venue, production, or session
- May happen through invite, public access, ticketing, or future will-call logic

Ticket
- A future access artifact that grants audience-level admission to a session or venue without broader authority

Will Call
- A future audience access mechanism where admission is granted from a prepared list or invite state at entry time

Workshop
- A special venue/environment where assets, props, sets, and reusable production materials are made or prepared

Asset Ingestion
- The controlled process of uploading, validating, clamping, storing, and registering an asset for future use

Ownership State
- The rights/status attached to an asset
- Initial examples:
  - personal
  - production_licensed
  - library_owned


Panel — a bounded UI region that groups controls or information
Tray — a compact control region, often temporary or retractable
Console — a role-specific control surface, usually director/operator facing
Presence — who is currently connected, where, and in what role
Attribution — displaying who performed an action
Delegation — granting a narrower authority from a higher authority
Ceiling — highest allowed permission boundary set by producer/operator
Default — normal allowed behavior unless overridden by production/session policy
Override — a temporary or higher-authority change that supersedes default behavior
Admission Policy — rules governing who may enter which venue/session and how


=== PERFORMANCE STRUCTURE ===

Venue
- Defines experience rules (space, audience, interaction)
- Example: the-cave, black box, classroom

Production
- A configured show/event
- Contains roles, assets, rules, and venue assignment

Session
- A live instance of a Production
- Contains active participants and current moment flow
- A Session is a temporary runtime window, not a state owner (Kernel 70
  §1.4). When linked to a Show (`sessions.show_id`), it projects that
  Show's persistent current Scene and state; ending the Session never
  resets the Show, and a later Session linked to the same Show resumes
  exactly where it left off. See "Show" and "Persistent Show Stage Fold"
  below.

Show Run (Production Run)
- Repeated Sessions of the same Production, grouped into one bounded
  container: a roster, an Audience Program, and a show-format/status label
  (planning/active/paused/completed/archived).
- "Show Run" is the product-facing/UI name; "Production Run" is this
  dictionary's original term for the same concept. They are the same thing,
  not two competing concepts.
- Implemented by the show_runs table and backend/internal/showruns
  (Kernel 66). Showing and Scene are explicitly separate concepts (see
  below) and are not part of a Show Run's own table.

Stage Management (Show Runs backstage surface)
- User-facing/map name (Kernel 68) for the Show Run backstage venue --
  internal slug, routes, and package name all remain "show-runs"/
  `backend/internal/showruns`; only the map tile label and page headings
  changed, to avoid churn.
- Visible only to Operator, Producer/Director at the venue's location, or a
  user with an active `crew` roster row on any Show Run at that location
  (visibility only -- a crew roster role does not itself grant manage/edit
  authority; that stayed out of scope for Kernel 68, see its reportback).
  Plain Audience/Player-only location membership no longer clears this bar
  (it did before Kernel 68 -- see access.ResolveVisibleVenues).
- Hiding the map tile does not touch the separate Audience Program route
  (`GET /api/show-runs/{id}/audience-program`, `GET /api/shows/{id}/program`)
  -- those stay reachable via their own direct link regardless of whether
  the viewer can see the Stage Management tile.

Show (Show Instance)
- The concrete playable/viewable instance of a Show Run: a planned future
  occurrence (no session yet), a live occurrence, a multi-session arc, or a
  completed/cancelled/archived one. Hierarchy: Production -> Show Run ->
  Show -> Session(s), with reusable Scenes (see below) staged into a Show
  via Show Scene Placements, not owned by it.
- Not the same as a Session (technical live runtime window, `sessions`
  table) and not the same as a Showing (Kernel 22's live 1:1
  audience-visibility wrapper around an active session, `showings` table)
  -- both remain untouched by Kernel 67.
- Implemented by the `shows` table and backend/internal/shows (Kernel 67).
  A Show has its own Audience Program (audience_title/
  audience_program_blurb) but inherits its parent Show Run's roster and
  authority wholesale -- it has no roster table of its own.
- `sessions.show_id` is a nullable, manually-set link (not wired into the
  `/session start` command flow) so a Session can optionally point back at
  the Show it belongs to.
- The Show, not the Session, owns the stage (Kernel 70 §4.1). A Show has a
  persistent `current_show_scene_placement_id` pointer and a
  `variables_json` key-value cache, both of which survive Session end --
  ending or rotating a Session never resets them. A later Session linked to
  the same Show resumes the same current Scene and state automatically,
  via `world.LoadVenueSnapshot` folding `actions` rows tagged with the
  Show's id (persistent) alongside the active session's own rows (see
  "Persistent Show Stage Fold" below) -- no synthetic copy/re-insertion
  step exists or is needed. Both fields are deliberately excluded from
  Show's own JSON serialization (`json:"-"`) since `HandleShowProgram` (the
  Audience-viewable endpoint) reuses the same struct; backstage callers
  read them from an explicit response field instead.

Persistent Show Stage Fold
- The mechanism behind "the Show owns the stage" (Kernel 70 §2, §4.3). The
  `actions` table gained a nullable `show_id` column alongside its existing
  `session_id`. A Cue's `go_to_scene`/`set_show_variable` actions write one
  action row with BOTH columns populated when an active session exists for
  the Show (not two rows), so the existing per-session action feed and the
  new persistent Show-scoped feed never double-count the same event.
- `world.LoadVenueSnapshot`'s stage-object replay
  (`reconcilePlacedElementsFromActions`) and its raw action feed both query
  `WHERE a.session_id = $1 OR ($2 <> '' AND a.show_id::text = $2)` --
  when a session has no linked Show, `$2` is empty and this reduces to
  exactly the pre-Kernel-70 `a.session_id = $1` filter, byte-for-byte.
  Ordering switched from `moment_id` (only unique/comparable within one
  session) to `ts` (comparable across sessions and Show-scoped rows alike).
- None of Kernel 70's three required Cue action types actually write
  stage-object-shaped actions (`act/place_element` etc.) -- `go_to_scene`
  writes a `cue/go_to_scene` marker row, `set_show_variable` writes
  `cue/set_show_variable`. The fold's *element-reconciliation* pass exists
  as forward-looking infrastructure for a future kernel's
  `reveal_object`/`hide_object` Cue actions (deferred this kernel, see
  "Cue" below); it is proven independently in
  `backend/internal/world/snapshot_test.go` using hand-inserted
  `act/place_element` rows, not by any action type Kernel 70 itself emits.

Scene
- A reusable, location-scoped authored/configured playable or viewable
  unit -- comparable to a standing set on a studio lot (Kernel 69, scope
  corrected by Kernel 70). A Scene is deliberately NOT a child row of one
  Show or one Production: the same Scene may be staged in zero, one, or
  many Shows under ANY Production at the same Victory location (e.g. a
  recurring "Character Making - Opening" Scene reused across one-shots run
  by different Producers at the same location). Cross-location reuse
  remains rejected.
- Implemented by the `scenes` table (`location_id NOT NULL REFERENCES
  locations(id) ON DELETE RESTRICT`) and backend/internal/scenes. Slug
  uniqueness is scoped to the location, not the originating Production.
  `source_production_id` (optional, nullable) remembers which Production
  the Scene originated under as provenance only -- it never gates reuse.
  Kernel 69 originally scoped this column as `production_id NOT NULL`;
  Kernel 70's migration (043) renamed and loosened it, backfilling
  `location_id` from each Scene's Production without deleting or
  duplicating any row.
- Statuses: draft, ready, retired, archived -- deliberately no `live`
  status; a Show's *current* Scene is tracked by `shows.
  current_show_scene_placement_id` (see "Show" below), not by a Scene- or
  placement-level status value. Archiving a Scene blocks *new* Show Scene
  Placements (CreatePlacement rejects an archived Scene) but never touches
  existing placements, which remain exactly as staged.
- Has both audience-facing fields (audience_title, audience_summary) and
  backstage-only fields (player_brief, director_notes, operator_notes) --
  only the audience fields (with a Show placement's own override applied
  first) ever reach a curated Audience Program view.
- `source_ref` and `config_json` exist only to reserve room for a future
  script/hyperlink system -- no script editor, hyperlink graph, or
  line-anchor system exists yet. Treat any future Script concept as linking
  *to* Scenes, not replacing them. Kernel 70 deliberately does not bind a
  Scene's `config_json` to the live PIXI stage-object system either (see
  "Base Scene" below) -- Scene composition remains metadata-level.
- Not to be confused with `frontend/venues/{first-theater,catharsis}/
  runtime/scene-nodes.js`, a PIXI.js canvas scene-graph helper predating
  this kernel and unrelated to the Scene domain object -- same word,
  different meaning (rendering "scene" vs. the playable-unit "Scene").

Base Scene vs. This Show's Version
- Two distinct editing targets Kernel 70 introduces for a reusable Scene.
  "Base Scene" is the shared `scenes` row itself -- editing it (via
  `PATCH /api/scenes/{id}`, Crew-eligible only for non-destructive fields)
  changes the standing set wherever it is used, across every Show/
  Production staging it. "This Show's Version" is a specific Show Scene
  Placement's own override fields (audience_title_override,
  audience_summary_override, director_notes_override, config_json) --
  editing it (via `PATCH /api/shows/{show_id}/scenes/{placement_id}`)
  changes only that one Show's dressing, never the shared Base Scene or any
  other Show's placement of the same Scene.
- Kernel 70 did not build a unified in-venue "Rehearsal editor" UI that
  visually composes Scene content on the live PIXI stage -- Scenes have no
  binding to the `elements`/`venue_layout_elements`/`actions` stage-object
  system. The Base-vs-This-Show distinction exists today at the
  metadata/text-field level (Scene Library page for Base Scene edits,
  Show detail page's placement rows for This-Show overrides); a future
  kernel would need to design how visual stage composition maps onto this
  two-layer model before building deeper Rehearsal tooling.

Show Scene Placement (Show Scene)
- The use of one reusable Scene inside one specific Show -- ordering
  (sort_order), an optional Venue override, and a small set of
  audience/director text overrides, none of which mutate the underlying
  Scene. UI calls this "Scenes in this Show" / "Add Scene to Show" /
  "Remove Scene from Show" and never surfaces the word "placement."
- Implemented by the `show_scene_placements` table (`UNIQUE(show_id,
  scene_id)` -- a Scene may be staged at most once per Show, but the same
  Scene can have a separate placement row in any number of other Shows).
  `scene_id` is `ON DELETE RESTRICT`: removing/archiving a placement is a
  status change, never a delete, so a Scene can never be silently orphaned
  out from under a Show's history.
- Statuses mirror Scene's own (draft/ready/retired/archived, no `live`). A
  placement's Audience Program visibility requires status = 'ready' and
  archived_at IS NULL -- draft-staged Scenes never leak to Audience.
- Curated Audience Program addition lives at `GET /api/shows/{id}/scenes/
  program`, deliberately a separate route from `GET /api/shows/{id}/
  program` (Kernel 66/67's roster-based Audience Program) rather than a
  merged response, to avoid backend/internal/shows importing
  backend/internal/scenes (which itself imports `shows` to resolve a
  Show's parent Show Run/Production) -- an import cycle. The Show detail
  page's frontend calls both routes and renders them together.

Cue / GO
- A stable, Show-Scene-Placement-scoped backstage control (Kernel 70 §6).
  Each Cue has a required internal/backstage name, an optional
  player-facing stage-button label, a trigger-permission scope, and an
  ordered JSON array of actions. The visible stage-button label is NEVER
  the Cue's identity -- a button always triggers the underlying Cue by id,
  so relabeling a button never breaks anything referencing the Cue.
- "GO" (or "Go Cue") is the act of executing a Cue's action list --
  `POST /api/cues/{id}/go`, client-idempotency-keyed per press (a repeated
  press with the same key replays the original result rather than
  re-executing; a genuinely concurrent duplicate press loses a DB unique-
  index race on `(cue_id, idempotency_key)` and receives
  `cue_execution_in_progress` rather than silently double-applying).
- Implemented by `cues` and `cue_executions` (migration 045) and
  `backend/internal/cues` (Kernel 70). Each action in a Cue's list executes
  in its own transaction, fail-stop (a failure does not roll back earlier
  actions in the same Cue, nor attempt the remaining ones) -- recorded
  outcomes are `succeeded`, `partial_failure`, or `failed`, never silently
  swallowed.
- Three action types are implemented this kernel: `go_to_scene` (sets the
  Show's current-Scene pointer, rejecting a target placement from another
  Show), `emit_game_event` (reuses `actions.StoreGameEventTrusted`, the
  existing Kernel 60 game-event mirror, minus its participant-role gate --
  Cue-trigger authority already gated the whole GO press) and
  `set_show_variable` (writes the canonical show_id-scoped actions row plus
  a `shows.variables_json` denormalized cache). `reveal_object`,
  `hide_object`, `enable_interaction`, and `disable_interaction` are
  explicitly deferred -- they would require extending the per-session
  visibility-layer derivation in `world/snapshot.go` to a second show-
  scoped source, which is the "second object model" this kernel's
  data-restraint requirement says to avoid without a fuller renderer pass.
- Trigger scopes: `director_crew_only` (default), `players_may_trigger`,
  `any_roster_member`. Audience can never trigger any Cue under any scope
  -- enforced as a hard floor in `cues.CanTriggerCue` independent of
  trigger_scope, not merely by omission from the roster-role checks.
- Crew may create/edit non-destructive Cues and press GO (including a GO
  that changes the current Scene) via
  `showruns.CanCrewPerformNonDestructiveEdit` -- the same underlying check
  as `CanViewBackstage`, reused rather than duplicated; the distinction
  that matters is which *write* endpoints call it, not a separate boolean.
  Crew cannot call the current-Scene-pointer endpoint
  (`POST /api/shows/{id}/current-scene`) directly outside Cue execution,
  cannot edit a Base Scene, and cannot archive/delete anything.
- Player-facing stage buttons: `GET /api/shows/{show_id}/scenes/
  {placement_id}/player-cues` returns a curated `{id, label}` list --
  only enabled Cues the calling viewer can actually trigger right now
  (Audience always gets an empty list). No trigger_scope, action payload,
  or internal_name of a Cue the viewer can't see leaks through this route.
  Rendered in First Theater/Catharsis as a small fixed-position button
  panel wired through the existing `session-sync.js` snapshot-apply
  pipeline (`updateStageCueControls`), not a deep PIXI-canvas integration.

Showing (live/runtime) vs. Show (scheduling/instance container)
- "Showing" (Kernel 22, backend/internal/showings) is the live, 1:1 runtime
  wrapper auto-created around an already-active Session -- it controls
  audience-view visibility and tags actions for replay/review.
  `showings.session_id` is NOT NULL UNIQUE and lazily created on first
  action-write; it has no notion of "not yet started" and is not a
  scheduling primitive.
- Kernel 66's note in this dictionary previously predicted that future
  pre-live scheduling would extend the `showings` table. A live code audit
  for Kernel 67 found that constraint too risky to loosen (20+ call sites
  in internal/actions/*.go, network/session_control.go, and
  identity/{discord_mic,join}.go depend on showings.session_id being
  non-null and unique). Instead, Kernel 67 built a separate `shows`
  table/package (see "Show (Show Instance)" above) as the scheduling/
  instance container, and left `showings` completely untouched. Any future
  kernel should treat `shows`, not `showings`, as the scheduling primitive.

Canonical Participation Context
- Kernel 71's single answer to "what is this user's role/access here,"
  resolved by `participation.ResolveParticipationContext`
  (backend/internal/participation). Before this existed, four independent
  tables each answered a related question with no agreed precedence:
  `location_memberships` (per-Location role, the Kernel-66+ source Show-Run/
  Show/Scene/Cue authority already trusted), the older `memberships`
  (per-venue-or-production-or-location, used only by the legacy
  `lookupVenueRole` feeding `world.LoadVenueSnapshot`'s `viewerRole`),
  `access_grants` (a boolean venue/production reach grant, no role of its
  own), and `show_run_roster_members` (Show-Run-scoped role, its own
  vocabulary including `player`).
- Precedence, highest wins, nothing lower may ever downgrade a role a higher
  step already found: Operator -> active `location_memberships` row ->
  active `show_run_roster_members` row -> any active `location_memberships`
  row at all (audience) -> legacy `memberships`/`access_grants`, read only
  as a last-resort upgrade from "none," never consulted if a canonical step
  above already resolved something.
- This is the fix for a real bug found during Kernel 70A's live checklist: a
  Producer/Director whose only grant was a `location_memberships` row (the
  normal shape for anyone bootstrapped or signed up after Kernel 66)
  resolved as `viewerRole = "none"` at their own venue, because the legacy
  `lookupVenueRole` queried `memberships` alone. `main.go`'s `lookupVenueRole`
  now delegates to the resolver (`participation.LegacyLookupVenueRole`)
  instead, keeping its three existing `/api/world/*` call sites unchanged.

Show Ticket / Player Punch / Director Punch / Valid Ticket
- Kernel 71's mutual-consent mechanism: the only ordinary path that creates
  an active Player row on a Show Run's roster. One compact record
  (`show_run_tickets`) represents both consent directions rather than
  separate invitation/request tables.
- A "punch" is one side's half of the agreement. The Player's punch and the
  Director's (or Producer's/Operator's) punch are each recorded
  independently, with who and when. Either side may punch first:
  Player-initiated (a request, status starts `pending_director`) or
  Director-initiated (an invitation, status starts `pending_player`).
- A ticket is "valid" only once BOTH punches exist. The single punch that
  completes it is one atomic transaction (`tickets.SecondPunch`): it locks
  the ticket row, verifies the punching side is the correct party (a Player
  can only punch for themselves; a Director's authority is re-checked
  against the locked ticket's own Show Run, never a client-supplied one),
  marks the ticket valid, and creates or reactivates exactly one Player
  roster row via `show_run_roster_members`'s existing partial-unique-index
  `ON CONFLICT` -- the same mechanism `showruns.AddRosterMember` already
  relied on -- so a duplicate roster row or a double-processed concurrent
  second punch is structurally impossible, not just application-checked.
- One punch alone grants nothing: no roster row, no venue access, no
  Character selection. A pending ticket may be declined (by the waiting
  side) or withdrawn (by the initiating side) before validation; both leave
  an auditable, resolved ticket row and grant nothing. Ticket scope is the
  Show Run, not one Show -- a valid ticket permits participation across
  every Show under that bounded Show Run.
- `showruns.AddRosterMember` and `UpdateRosterMemberRole` both reject a
  direct or promoted `role="player"` for non-Operator actors -- a ticket's
  second punch is the only ordinary route to that role. Operator retains an
  explicit, auditable override (the same shape as Kernel 66's Audience-block
  Operator override). All other roster roles (director, producer, crew,
  audience, guest, observer, custom) remain ordinary direct-add, unchanged.
- Future, explicitly NOT built this kernel: Audience tickets. Unlike Player
  tickets (Show-Run-scoped), a future Audience ticket would be
  single-Show-scoped and acquired through a future audience/marketing venue,
  not Audition Hall. `show_run_tickets.requested_role` is CHECK-locked to
  `'player'` specifically so that future kernel is an additive migration
  (widen the CHECK), not a schema redesign.

Selected Show Run Character
- The Character (`character_cards` row) a Player is currently presenting as
  for one specific Show Run, stored on `show_run_roster_members.
  character_card_id` (Kernel 71). Selectable/switchable freely by the
  rostered Player themselves, no Director approval required; must be active
  (`is_deleted = FALSE`) and owned by that Player.
- Deliberately independent of two older, unrelated "current Character"
  concepts: `active_user_characters` (site-wide, one row per user, read by
  Greenroom/venue runtimes generally) and `current_session_personas`
  (Session-scoped, ephemeral, cleared when a Session ends). Conflating
  either with Show-Run-scoped selection would leak one Show Run's presented
  identity into an unrelated context, or make the selection only "stick" for
  the currently-live Session. The one connection point:
  `world.LoadVenueSnapshot`'s `TheaterContext` now reads
  `show_run_roster_members.character_card_id` (joined against
  `character_cards.is_deleted`) as its "has this Player chosen a Character"
  signal, replacing the old `current_session_personas` EXISTS check. An
  archived/deleted selected Character is treated exactly like no selection
  at all -- the Player is prompted again, never left pointing at a vanished
  Character.

Show Short Code
- A short, human-typeable, per-Show identifier (`shows.short_code`),
  auto-generated at Show creation with no client input, from a
  confusable-excluding charset (no `0/O`, `1/I/L`). Director/Producer/
  Operator may edit it within their authority. Deliberately a new column,
  not a repurposing of the existing per-show-run `slug` (unique only within
  one Show Run and used for a different job, page routing).
- Uniqueness is location-scoped (joined through `show_runs.location_id`,
  since `shows` has no direct location column) and case-insensitive.
  Resolution (`GET /api/shows/by-code`) returns only show/show-run/location
  identifiers -- never roster, variables, or other backstage state, so
  Audition Hall's "Join a Show" lookup and an unauthenticated-adjacent
  glance never leak backstage information.
- Used by `/showtime <code>` and by Audition Hall's Show-Run lookup when a
  Player wants to request to join (see "Show Ticket" above) -- resolving a
  code for that purpose must tell the Player the resulting ticket is
  Show-Run-scoped, not limited to the one Show named by the code.

Showtime
- The one Director action (Kernel 71) that replaces separately operating
  Production/Show-Run/Show/Session start plus a manual venue picker: resolve
  a Show by its short code, derive which venue it belongs on, and
  start-or-resume its live Session -- all through the existing, unmodified
  Kernel 70A `shows.StartShowSession`.
- Venue derivation: if the Show already has a persistent current Scene
  (`current_show_scene_placement_id`), use that placement's resolved venue
  (its own override, or its Scene's default). Otherwise, scan every Scene
  Placement staged on the Show; if they resolve to exactly one distinct
  venue, use it (and set that placement as the Show's current Scene as a
  side effect, since it had none yet); if zero or more than one distinct
  venue is found, ask instead of guessing (`needs_venue_choice` in the
  response) -- Showtime never silently picks among ambiguous venues.
- Mic always starts off; `StartShowSession` never touches mic state at all,
  so this is true by construction, not by an explicit "turn mic off" call.
  The success response suggests `/mic hot` as a separate, deliberate next
  step.
- `/showtime end` ends only the technical live Session -- the Show's
  current Scene, its variables, its roster, and every Player's Character
  selection are untouched by construction (no write path in
  `showtime.End` reaches any of those tables); the Show may be resumed
  later exactly where it left off, matching "Persistent Show Stage Fold"
  above.
- Implemented as an in-app "legacy" command (`commands/registry.go`,
  `POST /api/showtime/control`), matching `/session`'s existing precedent,
  not a real Discord-native slash command the way `/mic` is -- a confirmed
  scope decision, not an oversight; a Stage Management button reaches the
  same endpoint.

Trailer Face Ready
- A computed (not stored/durable) readiness verdict on whether a user has
  intentionally set up a usable Trailer Face: a stage name plus at least one
  visible Face field beyond bare defaults (Kernel 68 §1.1, §3.1).
- Computed live from the existing Kernel 61 projection
  (playerprofile.ProjectTrailerFace/TrailerFaceReady) -- no new "published"
  boolean or timestamp was added; a fact only ever exists if the owner
  explicitly committed it, so field-presence is a reliable readiness signal
  on its own.
- reason_code values: face_ready, missing_face_commit (no stage name),
  missing_visible_face_field (stage name set but zero visible facts),
  not_authenticated.
- Third Place unlock rule: the Third Place venue tile is hidden from the map
  until Trailer Face Ready is true for the viewer (access.
  ResolveVisibleVenues, `trailer_face_ready` visibility reason). This
  *replaced* Third Place's (and Trailers') prior producer/director/cast/crew
  role restriction -- Kernel 68 found that restriction was a stale carryover
  from the old Trailers-only rule that pre-dated Kernel 65's actual intent
  (a general social space for anyone with a Face, not a staff-only one).
  Trailers itself is now open to any authenticated user regardless of role.
  Direct Third Place API access (leaving a Headshot) is separately gated the
  same way and returns a clean 403 `trailer_face_not_ready` for an unready
  caller; viewing the Headshot Commons list/history stays open to any
  authenticated user, since nothing not-yet-ready is ever placed into it.

=== SPACE MODEL (the-cave v1) ===

World
- Bounded 3D space with a central plane

Plane (Ground)
- Primary interaction surface (y = 0)

Stage
- Shared focal area
- Always visible to audience

Audience Area
- Viewing position facing stage
- Default perspective for participants

Backstage
- Hidden system area
- Used for tools, preparation, hidden elements

Interface Layer (Overlay)
- UI elements anchored in space (banners, indicators)

---

=== CORE ENTITIES ===

Element
- Any object that can exist in the system
- Examples: fire, text, image, prop, reaction

Library
- Producer-owned reusable element collection

Script / Ruleset / Module
- Defines structured behavior for a Production
- Can be rigid (script) or flexible (improv/game)

---

=== TIME MODEL ===

Moment
- Atomic unit of time + state
- Contains all actions and visibility at an instant

Past
- Immutable (no retroactive contradiction)

Present
- Active manipulation

Future
- Undefined

---

=== VIEW MODEL ===

View
- A participant-specific projection of a Moment

Surface
- A display/control plane (stage, backstage, overlay)

Segment
- A grouping of participants (NOT a role)
- Examples: front_row, late_entry, VIP

Rule:
- Same Moment → Different Views

View = f(MomentState, DirectorRules, Role, Segment, ClientState)

---

=== ROLES ===

Producer
- System owner
- Highest authority

Director
- Controls stage, visibility, and audience perception

Cast (Actors)
- Perform and manipulate elements

Crew
- Support roles (tools, operations, automation)

Audience
- Observes and reacts
- No direct stage control by default

---

=== REACTION MODEL ===

Reaction
- A feedback signal attached to a moment

- clap, laugh, boo, etc.

Routed:

- Role-dependent
- Configurable

production

library

- System truth accumulates
